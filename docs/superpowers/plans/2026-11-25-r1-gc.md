# R1 — Memory reclamation (mark-sweep collector) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reclaim unreachable memory in compiled programs, so that long-running data-processing loops run in bounded memory with byte-identical output.

**Architecture:** A non-moving mark-sweep collector, as described in the spec:
- an allocator built from 64 KiB size-class pages and large blocks, with a page table that also resolves interior pointers;
- conservative roots: the program-thread stack and registers, `.data`/`.bss`, and the thread-local pending-exception payload;
- `SCAN`/`NOSCAN` block kinds;
- a collection threshold of `max(4 MiB, live)`;
- two diagnostic modes, `SIYO_GC_STRESS` and `SIYO_RT_STATS`.

**Tech Stack:** C11 runtime (glibc/pthreads), Java 21/JUnit 5 harness, clang 19.

**Spec:** `docs/superpowers/specs/2026-11-25-memory-reclamation-design.md`; goal `docs/RUNTIME_READINESS_GOAL.md`.

## Global Constraints

- Program output (stdout, stderr, exit status, written files) must stay byte-identical to the existing expectations for every corpus, module and ledger case, with and without `SIYO_GC_STRESS`.
- The `SIYO_RT_STATS` line goes to stderr only when the variable is set. Existing tests never set it.
- RED first: commit the memory-bound tests before the collector. The RED run log is preserved verbatim under `docs/evidence/r1-gc/red/`.
- RED sizes must stay below the bounded scope: never-free peak RSS no higher than about 400 MB per workload run. No known runaway input is ever run.
- Host rule:
  - Plain `mvn` is the bounded wrapper (768 MiB).
  - Manual runs use `python3 ~/.hermes/automation/siyollvm/bounded.py --`.
  - Scratch files go only under `$TMPDIR`.
  - clang is `$SIYOLLVM_CLANG`.
- Runtime C stays warning-free (`RuntimeBuildNativeTest`) and keeps the existing `RuntimeIrTest` classification discipline.
- Commits are authored by `urunsiyabend@gmail.com` and end with the co-author line.

## Review Focus

- **Missing roots.** A heap pointer may be held only in:
  - a callee-saved register;
  - a C runtime local across an allocating call;
  - the pending-exception TLS slot;
  - the box cache;
  - IR globals of every module unit;
  - map and array growth mid-copy.

  The whole corpus under `SIYO_GC_STRESS=1` must match byte for byte (Task 2).
- **Interior pointers.** String data pointers into a `SiyoBuf`, and item pointers. Covered by the stress corpus and by a C-level allocator test (Task 2).
- **Cycles and aliasing.** Cover struct cycles, an array containing itself, and maps of structs referring back. Each must be reclaimed when dropped and survive while any alias remains. Test `gc_cycles` workload (Task 1) plus the stress corpus.
- **Exceptions in loops.** Thrown payloads are reclaimed after being caught, and an uncaught exception still prints correctly under stress. Test `gc_exceptions` workload (Task 1).
- **Large blocks and growth.** Cover a 10^6-element array, map growth past many rehashes, and string buffers past 2 KiB (large path). Test the `gc_arrays` and `gc_maps` workloads (Task 1).

### Task 1: Memory-bound regression suite (RED)

**Files:**
- Create: `src/test/resources/memory/<workload>/main.siyo`, with modules where needed. Each workload reads N from `main.args` or its arguments and prints a checksum line.
- Create: `src/test/java/siyollvm/nativegate/MemoryBoundsNativeTest.java`.
- Create: `scripts/memory-oracle.sh`, or extend `reference-oracle.sh` usage, to generate the expected output per N with the JVM reference.

**Interfaces:**
- Workloads:
  - `gc_strings`: build and discard strings per iteration, with `+=` inside a per-iteration local;
  - `gc_arrays`: arrays created, filled and dropped, plus one growing array kept live;
  - `gc_maps`: maps rebuilt per iteration;
  - `gc_structs`: struct churn;
  - `gc_cycles`: struct and array cycles dropped;
  - `gc_exceptions`: throw and catch with string payloads;
  - `gc_modules`: allocation inside an imported module's function;
  - `gc_lines`: writes a file of N lines, then reads and aggregates it in a loop, keeping a small live map.
- For each workload, `MemoryBoundsNativeTest`:
  - builds once;
  - runs at N1 < N2 < N3, chosen so that never-free memory reaches tens to hundreds of MB at N3 but stays within the RED cap;
  - sets `SIYO_RT_STATS=1`;
  - checks that stdout equals the JVM-generated expectation for that N;
  - parses `rss_peak_kb` from the last stderr line and asserts `rss(N3) <= 64 MiB` (or a per-workload bound stated in the test with a justification) and `rss(N3) <= 1.5 × rss(N2) + 8 MiB`.

  A missing stats line is a failure. This is how the RED stage fails today: the current runtime does not print the line yet. That is a legitimate but uninformative RED. To get an informative RED as well, temporarily add the stats line before the collector, in a separate first commit, so the RED shows real growth numbers.
- **Ordering:**
  1. Commit 1 (runtime): add `SIYO_RT_STATS` reporting only, with no collector.
  2. Commit 2: add the tests.
  3. Run them and preserve the RED log and the measured RSS table under `docs/evidence/r1-gc/red/`.
